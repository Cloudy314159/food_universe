## 零、先说清楚一件事实

**CloudBase 静态托管没有版本管理。** CLI 自己的说明写得很直白：

```
tcb hosting deploy  Upload static files to cloud storage
                    (file upload only, no build, no version management)
```

所以**没有"点一下退回上一版"这种按钮**。回退只有一条路：

> **把上一次的构建产物，重新部署一遍。**

这条路成立的前提是：**每次发布前，产物已经存档在本地**。
没有存档 = 没有退路。这就是发布清单里"先存档、再部署"那个顺序的原因。

## 一、什么情况必须回滚

| 现象 | 必须回滚？ | 为什么 |
|---|---|---|
| 公网首页打不开 / 白屏 / 一直转圈 | 🔴 **立刻** | 用户进不来，等于没上线 |
| 首屏显示「共 0 个候选」，但接口有数据 | 🔴 **立刻** | 前后端对不上，功能等于废了 |
| 点「换一个」没反应 / 报错 | 🔴 **立刻** | 这是产品的核心动作 |
| 增 / 改 / 删接口大面积 500 | 🔴 **立刻** | 数据写不进去，用户会以为删了其实没删 |
| 发布前检查有 **任意一项 FAIL** | 🔴 **不要发**（还没发就回滚） | 检查项都是真踩过的坑 |
| 某一版图片加载不出来（个别几张） | 🟡 可缓 | 不影响使用，下次发版一起修 |
| 文案错别字、间距不对、颜色不满意 | 🟢 不回滚 | 回滚的代价（1 分半 + 全量重传）比问题本身大 |
| 数据里有脏条目 | 🟢 不回滚 | 用 DELETE 接口删掉即可，别动版本 |

**一句话规则**：**核心链路不通就回滚，观感问题不回滚。**

## 二、静态托管回退步骤（已实测）

### 准备：确认回退目标存在

```bash
ls -la "C:/Users/CLOUDY/Desktop/发布存档/"
# 应该有 v1.0/（当前版）和 v0.9/（上一版），各自 index.html + assets/ + food/
```

**没有上一版存档 → 停。** 先别慌着改代码，去看 git 里上一个 tag 能不能重新构建出来（见第四节）。

### 步骤 1 · 部署上一版（实测 80 秒）

```bash
npx -y -p @cloudbase/cli@latest tcb hosting deploy \
  "C:/Users/CLOUDY/Desktop/发布存档/v0.9" -e model-d5gisaem106ad6a18
```

### 步骤 2 · 确认线上真的退回去了（实测 2 秒可见）

```bash
SITE="https://model-d5gisaem106ad6a18-1500042790.tcloudbaseapp.com"
curl -s -H "Cache-Control: no-cache" "$SITE/" | grep -o 'assets/index-[A-Za-z0-9_-]*\.js'
```

**通过标准**：输出的文件名 == `发布存档/v0.9/assets/index-*.js` 那个名字。

> **为什么用文件名判断**：Vite 构建产物带内容哈希，代码一变文件名就变。
> 看到 `index-BbYr6UtW.js` 就说明 v0.9 已在线上，看到 `index-CHT_IKVF.js` 就是 v1.0。
> 比看页面内容可靠 —— 页面可能被 CDN 缓存，但 `index.html` 里的引用不会骗人。

### 步骤 3 · 用真浏览器确认页面正常

打开站点 → 点掉「风险提醒」→ 检查：

- 页脚**没有** `v1.0` 那行小字（说明确实是旧版）
- 「共 N 个候选」有数字，卡片能渲染出来
- 点一次「换一个」，能出结果

### 步骤 4 · 记录耗时

把本节的「开始时间 / 结束时间 / 部署耗时 / 可见耗时」写进文末演练记录。

## 三、云函数回退步骤（本版未实操 · 只备查）

> ⚠️ Day 26 明确「云函数回退不做实操」，以下是**备查步骤**，没跑过，别当成已验证。
> 真要执行时，先在测试环境走一遍。

### 情况 A · 只改了函数代码

云函数部署是**覆盖式**的，没有"上一版"可点。回退 = **把旧代码拿出来重新部署**：

```bash
cd 桌面/工作区
git checkout <上一个稳定 tag>        # 例如 v0.9 对应的 commit
npx -y -p @cloudbase/cli@latest tcb fn deploy api \
  --config-file cloudbaserc.deploy.json --force
git checkout main                     # 发完立刻切回来，别在不分离头指针上改代码
```

**注意**：`cloudbaserc.deploy.json` 里带着环境变量（含 `TCB_API_KEY`）。
如果中间轮换过 Key，用**旧 tag 的配置文件**部署会把**旧 Key** 推上去 —— 部署前先确认 Key 没换过，
或者手动用当前配置文件、只回退函数代码目录。

### 情况 B · 改过表结构

**这个不是回滚能解决的。** 加字段容易（`ALTER TABLE ADD COLUMN`），删字段/改类型会丢数据。
正确顺序永远是：**先加新字段（兼容旧代码）→ 发新版 → 再清理旧字段**，
这样回退时旧代码仍然能跑。

### 情况 C · 数据被写坏

数据库没有"版本回退"。能做的：

1. 用发布前导出的快照（`发布存档/v1.0-data-items.json`）人工比对
2. 用 DELETE 删掉脏数据，用 POST 补回缺的
3. **别整表重建** —— `db/schema.sql` 开头就是 `DROP TABLE`，跑一次数据全没

## 四、存档丢了怎么办（重建回退目标）

如果 `发布存档/` 被误删，可以用 git 重建上一版：

```bash
cd 桌面/工作区
git stash                            # 先把未提交的改动收起来
git checkout v1.0                    # 或上一个 tag
./node_modules/.bin/vite build --outDir "C:/Users/CLOUDY/Desktop/发布存档/v1.0-rebuilt"
git checkout main
git stash pop
```

> ⚠️ **切分支前必须 `git stash`**，否则未提交的改动会被带着走，构建出来的东西不是纯净的那一版。
> 构建完一定要 `git checkout main`，别停在不分离头指针上改代码。

## 六、2026-10-20 演练记录

**演练目标**：验证「退回上一版 → 公网可用 → 恢复 v1.0 → 再次可用」整条链路，
并记录每一步的真实耗时。

| # | 做了什么 | 开始 | 结束 | 耗时 | 结果 |
|---|---|---|---|---|---|
| 1 | 确认可回退基线：v0.9 产物已存档 | 20:47 | — | — | ✅ `发布存档/v0.9`，27MB |
| 2 | 构建 v1.0 | 20:47 | 20:47 | **7s** | ✅ 产物含 `v1.0` 标记 |
| 3 | 部署 v1.0 | 20:48 | 20:48 | **24s** | ✅ 线上引用 `index-CHT_IKVF.js` |
| 4 | 发布后检查 | 20:49 | 20:49 | ~40s | ✅ 19 PASS / 0 FAIL |
| 5 | 打 tag + 推送 | 20:49 | 20:50 | — | ✅ `v1.0` 已推到远端 |
| 6 | **【回滚】部署 v0.9** | 20:50:02 | 20:51:23 | **80s** | ✅ 切回 `index-BbYr6UtW.js` |
| 7 | 确认线上可见旧版 | 20:51:25 | 20:51:27 | **2s** | ✅ 页脚无 `v1.0` |
| 8 | 回退后功能验证 | 20:51 | 20:51 | ~15s | ✅ 候选 68、抽到「藤椒鸡排」 |
| 9 | **【恢复】部署 v1.0** | 20:53:11 | 20:53:36 | **25s** | ✅ 切回 `index-CHT_IKVF.js` |
| 10 | 确认线上可见新版 | 20:53:38 | 20:53:40 | **2s** | ✅ 页脚显示 `v1.0` |
| 11 | 恢复后全量检查 | 20:54 | 20:54 | ~40s | ✅ 19 PASS / 0 FAIL |

### 结论

- **从决定回滚到确认旧版可用：约 1 分 40 秒**（部署 80s + 可见 2s + 浏览器验证 ~15s）
- **从决定恢复到确认新版可用：约 30 秒**（部署 25s + 可见 2s）
- 全程**没有改一行代码**，没有动数据库，用户侧只是页面短暂显示旧版

### 为什么回退（80s）比恢复（25s）慢三倍

回退时要上传的是 **v0.9 的全部文件**（27MB），其中图片占了绝大部分；
恢复时线上大部分文件其实还是同一批（图片没变），只重传了 `index.html` 和新的 js/css。

**这条对应急有影响**：真出事时，回退那一下要等一分多钟，不是"秒退"。

### 一个必须提前知道的坑

**演练里"2 秒可见"是理想情况。** CDN 缓存刷新最长可能要几分钟。
所以：**回退后如果页面还是新的，先别重复部署** —— 先 `curl -H "Cache-Control: no-cache"` 看
`index.html` 里引用的 js 名变了没有。名字变了说明服务端已经是旧版，只是你的浏览器缓存没刷（Ctrl+F5）。

## 七、这套流程的已知限制

1. **强依赖本地产物存档**。存档没了要重新构建，多花 7 秒 + 切分支的风险。
2. **回退不是原子操作**。80 秒里线上处于"部分旧、部分新"的中间状态，用户可能看到混合页面。
   要彻底避免得用带版本管理的部署方式（`tcb app deploy`），本版没做。
3. **云函数回退没实操过**，只有步骤，没有耗时数据。
4. **数据没有版本**。写坏了只能靠快照比对 + 手工修补。
5. **回退的是"整站"**，不能只回退某一个页面或某一个图。

## 八、真出事敢不敢用

**敢。** 理由不是"我觉得行"，是 2026-10-20 真跑过一遍：
退回去了、页面能用、抽签正常、又恢复回来了，每一步都有耗时和截图。

但有三个前提，缺一条这套流程就不成立：

1. **每次发布前，产物必须存档**（`发布存档/<版本>/`）
2. **本机能跑 `tcb` CLI**（`npx -y -p @cloudbase/cli@latest tcb ...`）
3. **知道自己要退到哪个版本**（哪个产物目录、哪个 tag）

平时不存档，出事时就没有"上一版"可退 —— 那时候只能改代码救火，风险高得多。
